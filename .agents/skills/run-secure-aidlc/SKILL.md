# Run Simplified Secure AI-DLC

## Áp dụng tại Lost & Found

Gọi `$run-secure-aidlc` với UC spec và phạm vi SCN để triển khai sản phẩm, hoặc với UC nghiên cứu để mở lượt nghiên cứu. Đưa API spec nếu đã xác định hoặc để skill theo liên kết từ UC. Để tiếp tục, đưa run record hay ID định danh duy nhất. Cả hai dùng các bước dưới đây. Mã sản phẩm đi qua entry point hiện có trong `apps/`, còn lượt nghiên cứu giữ đích `finalsource/`. Chỉ đưa kết quả nghiên cứu vào sản phẩm qua thay đổi được review.

Use [references/workflow.md](references/workflow.md) for run state, downstream skill boundaries and repair authorization. Resolve technical constraints from [references/project-context.md](references/project-context.md). Use one run record for decisions and source-bound evidence. Stage and repair durations are outside collection and completion criteria.

1. **Identify the run.** Accept a readable UC spec or research `uc-*.md` and optional project-context paths. For scenarios using an API, read the supplied or referenced API spec and record its version with the UC and decision sources before drafting. For other scenarios, record their enforcement layer. For a resume, accept the existing run record or an unambiguous UC/run ID and continue from its last verified checkpoint. Check project instructions, artifact compatibility and the required delegation capability. Ask only about decisions that change the approved work or prerequisites the agent cannot satisfy.
2. **Draft and approve.** Delegate the proposed security scope, relevant schema and Prompts A–F to a **GPT-6.1 Terra, medium reasoning** sub-agent. Use standard mode if the tool exposes that setting. Pass the immutable UC, applicable API spec and relevant project constraints with their source paths. Persist selected SEC IDs, rationale and corresponding Prompt E criteria. Use the [drafting outline](references/workflow.md#drafting-without-project-templates) when project templates and downstream skills do not cover the run. The orchestrator reviews the drafts against the UC, API and project constraints, requests focused corrections, then presents the exact bundle for approval by the requester or researcher. Bind approval to that bundle and repeat approval for material changes. Begin source generation and apply schema changes only after approval.
3. **Generate source.** The orchestrator implements the approved bundle in the selected destination and records the initial source revision. For product work, inspect the existing entry point and preserve callers' behavior outside the requested scope. Apply a migration when confirmed behavior requires it and the approved scope covers it. Use **GPT-6.2 Sol** if the main model is configurable. Otherwise continue with the active model and record what is known. Use the relevant FE/BE skills and permitted build or lint checks. Pass the approved project constraints, applicable API spec and source references.
4. **Capture the first pass.** With the initial source intact, gather source, configuration and build evidence. For generated research FE/BE, gather authorized Docker smoke evidence on that same source when available. For product work, use the approved runtime checks for the project. Record failed or unavailable checks. Delegate a full assessment of every frozen Prompt E SR and applicable project constraint to **GPT-6.1 Terra, medium reasoning**. Persist the evidence-backed `first_pass_security` rows and counts against the initial revision before any repair. If runtime evidence is missing, record the gap and continue independent checks.
5. **Repair and verify.** The orchestrator screens each evidenced defect, applies one minimal correction per recorded repair and delegates one focused re-audit of the affected SRs and related impacts. Verify the corrected build/runtime where applicable. Pause automatic repair after **10 total repair attempts** across all categories. Further attempts require a recorded, explicit researcher request or approval for this run and the additional scope. See the [repair authorization rules](references/workflow.md#repair-authorization-and-stop-conditions).
6. **Finalize.** Run the authorized runtime checks on the final source. For generated research FE/BE, this requires researcher-authorized Docker smoke. For product work, use the approved runtime checks, such as the repo's existing integration suite or local smoke. If runtime reveals an actionable source defect, return to step 5 within the authorized limit. Delegate a final assessment covering every frozen SR and applicable constraint on the same revision. Reuse prior evidence when its applicability to that revision is established. Record the final source hash and result in the run record only when the completion conditions are met. Render Markdown on request.

The orchestrator owns state, source changes and calls to audit and Docker. The auditor receives the task, approved Prompt E and scope, relevant project constraints, source revision and evidence paths, plus related repair evidence for re-audits. It returns statuses, evidence, findings and gaps without modifying implementation source. Reuse a suitable audit agent or start a fresh one with the same bounded context. If the required sub-agent model or reasoning cannot be selected, report that once and ask for a decision covering the affected work. Record any authorized substitution. Unsupported standard mode alone does not block the run.

For authorized runtime checks, prepare minimal synthetic data and use the access path in the approved scenario, including normal authentication when required. Reuse existing authorization within scope. Try permitted alternatives for blocked browser actions and record any verified prerequisite the requester or researcher must supply. Report phase, artifacts and the exact remaining blocker or decision. Research uses build, lint and smoke evidence without creating or running test cases. For product work, run applicable existing suites against the same UC version when available, alongside the source audit. Report the UC version, SCN, changed files, checks run and any remaining coverage gaps in the handoff.
