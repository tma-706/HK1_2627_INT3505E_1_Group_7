# Derive load scenarios from product behavior

## From behavior to traffic

1. Read SCN/PERF in the UC specification and the referenced contract. Use source code or usage data where available to confirm behavior and assumptions. List actors, triggers, required and conditional steps, API calls, think or wait times, data sizes, and shared resources. Identify the outcome to verify, such as successful bookings before a deadline or time to drain a queue.
2. Add a table to `test-plan.md` by business period, such as normal hours, registration opening, or batch intake. Record journey starts per time period, source, and confidence. Prefer quantitative requirements for the run, logs or analytics for the relevant period, business plans, and previous measurements. Use source code to identify behavior and technical limits. Account counts, worker counts, and staging ceilings alone do not establish demand.
3. Convert demand by phase. If journey j starts at rate λj per second and makes an average of cj,e calls to endpoint e per journey, expected RPS for e is the sum of λj × cj,e. Include branch probabilities, polling, and retries specified by the contract. Weight journeys by starts and derive request mix after conversion. For batches or bursts, preserve the arrival distribution over time and measure backlog and completion time when relevant.
4. Choose a model that matches how demand arises. For known concurrent sessions, model sessions and action pacing. For independent arrivals, schedule an arrival rate and measure actual starts. When using a Locust loop as an approximation, estimate active users as starts per second × average loop duration including waits, then validate with a pilot. Slow responses can reduce the offered load of a closed loop. Record any shortfall.

## Select and finalize profiles

- Assign IDs that reflect the business question. For each profile, record the rationale, environment, journeys, data provisioning, phased load targets and units, load model, wait time, ramp-up, hold and recovery periods where applicable, required endpoint sample counts, success criteria, load ceiling, and stop conditions. Derive duration from business timing, observation cycles, and sample needs. Select spike, soak, or breakpoint tests when an event, risk, or capacity question warrants them.
- Without actual traffic, use sourced active user counts, action frequency, job schedules, or forecasts to form a hypothesis. Record the estimated range, sensitivity, and validation method. When evidence cannot establish representative load, build an exploratory profile from real journeys within known environment limits. Use a pilot to measure loop time, calls, and load-generation capacity. Record missing demand inputs separately. The pilot validates generator configuration and business data validates demand.
- Save agreed parameters to the project's `workloads.yml` or existing format. Store profiles by ID and map each CI stage to required IDs. Use the same IDs across the plan, Locust, `slo.yml`, and reports. The runner reads this configuration and fails on a missing profile or empty gate mapping. When replacing old tier configuration, update callers and retain result history.
- Compare demand with environment limits. Record the business target, permitted load, and scope of valid conclusions. Before the formal run, verify actual arrival rates, endpoint mix, concurrency, and sample counts against the plan. Adjust the generator and save the configuration version. Regenerate affected profiles when demand or the journey changes. Use the same configuration version for regression comparisons.
