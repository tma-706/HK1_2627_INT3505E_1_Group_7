# SOA course guide for contract design

Use the indicated PDF pages to trace the decision back to the course. The page numbers count PDF pages from 1. Apply the decision and its check to the project at hand. The framework demos and numeric exercise settings are examples.

| Course material | Decision to make | Evidence in the design |
| --- | --- | --- |
| B1 · Giới thiệu về API và Web Services, pp. 4–16 | Identify the consumer, interaction and compatibility constraints. Consider REST/JSON for resource access, GraphQL for varying client projections, gRPC for a typed streaming boundary, or SOAP/WSDL for an existing integration. One service can have several consumers. | Name the selected style, its contract artifact and the requirement driving it. Keep implementation and persistence details private. |
| B2 · Kiến trúc REST và HTTP Fundamentals, pp. 5–22 | Use self-contained requests, resource identifiers, representations and meaningful methods. Specify safety, idempotency, cacheability and content negotiation independently. Model navigable links when consumers need to discover available transitions. | Document PUT replacement versus PATCH semantics. A repeated DELETE may return a different status while preserving the intended effect. Specify media types, relevant headers, and any cache policy per representation. |
| B3 · API Design Principles và Best Practices, pp. 5–22 | Use consistent collection/item/subresource names, plural nouns and stable identifier paths. Use a query for supported filters, sort order and field projections. Choose success and error semantics by outcome. | A synchronous creation can return 201 with Location. A 204 has no body. Use a consistent error contract, e.g. RFC 9457 with application/problem+json, stable problem types and useful field errors. If present, the problem status matches the actual HTTP status. |
| B4 · API Specification và OpenAPI, pp. 7–24, 31–32 | Use the contract to drive implementation and documentation. Select the OAS dialect supported by consumers. Model parameters, request bodies, responses, shared schemas and security declarations. | Produce stable unique operationIds, required path parameters, resolvable references, concrete examples and explicit intentional public operations under global security. Apply OAS 3.0 nullable or OAS 3.1 JSON Schema null types according to the selected dialect. |
| B5 · Data Modeling & Resource Design, pp. 4–14, 18–28 | Derive resources from workflows, then identify identity, cardinality and ownership. Nest for real containment. Give a relationship with its own metadata or lifecycle an addressable representation. Choose page navigation and projections for the client's access pattern. | Show the resource list and relevant relationships. Separate create/update/read shapes, writable fields, absent vs null and server-managed attributes. Give changing collections a deterministic order and tie-breaker. |
| B6 · Auth, pp. 3–6, 9–26 | Distinguish caller authentication, delegated authorization, token format and object-level policy. Choose the mechanism for the client. Specify scoped API keys where suitable, OAuth authorization code with PKCE for a delegated public client, or client credentials for a suitable machine client. Use OIDC for sign-in if required. | State the credential carrier, role/scope and owner/tenant predicate. For JWT access tokens, define trusted issuer, audience, accepted algorithms, time checks and key rotation. Define 401 with an applicable challenge and 403 for insufficient permissions, or a consistent resource-concealment policy. |
| B7 · Backend Service, pp. 3–6, 19–23, 29–37 | Translate backend realities into contract guarantees. Separate transport validation, domain invariants and transaction boundaries. Bound related-data expansion, account for N+1 reads and bounded resource pools when relevant. | State what commits atomically, how conflicts surface and what a client can safely retry. Define internal liveness/readiness and structured correlation for an operated service. Keep framework scaffolding outside a specification-only request. |
| B8 · API Testing, pp. 4–15, 16–24, 27–33 | Choose unit, integration, provider/consumer contract and end-to-end checks by risk. Make client-observable behavior, side effects and schema conformance testable. For performance work, specify a representative journey, environment and workload. | Write cases as setup → call → status/shape/effect. Consider lint and compatibility diff in CI, provider/schema checks and consumer expectations on integration boundaries. Announce deprecation and sunset under the provider's actual policy. Keep dates and notice periods open if unspecified. |

## Review an OpenAPI deliverable

- Match path placeholders and declared parameters, operation IDs and all references. Include descriptions for responses and specify the actual media type, success schema or empty body.
- Separate create/update/read validation and check examples against required fields, enums and types. Describe cross-field rules and business conflicts in prose when the schema cannot express them.
- Check effective security at operation level. Security Requirement Objects listed as alternatives express OR. Schemes in one object express AND. For an HTTP bearer scheme use an empty scope array in OAS 3.0; describe application RBAC separately. If OAuth scopes are used, declare them in the appropriate flow and reference them on the operation.
- For governed APIs with a previous contract, compare against that version. For a new API with no baseline, state that fact. Select a validator matching the OAS version. A YAML parse alone only checks syntax.

Standards for the wire contract are [HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html), [Problem Details](https://www.rfc-editor.org/rfc/rfc9457.html), [OpenAPI 3.1.1](https://spec.openapis.org/oas/v3.1.1.html) and [OAuth 2.0 Security Best Current Practice](https://www.rfc-editor.org/rfc/rfc9700.html).
