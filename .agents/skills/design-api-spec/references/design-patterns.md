# API design patterns

Select a pattern when the SRS contains the corresponding interaction. Record the trigger, concrete operation, consumer-visible behavior, trade-off and one acceptance case. Adapt identifiers and examples to the existing contract.

| When the consumer needs to… | Specify in the contract | Verify with an example |
| --- | --- | --- |
| Browse or synchronize a collection | Choose page/offset for bounded sets requiring random page access, or cursor/keyset for large changing feeds. Document the default and maximum page size, supported filters/sort, tie-breaker, end-of-list marker, cursor validity and consistency under mutation. Bind an opaque cursor to its filter/order and applicable scope. Reauthorize each call. | Two records share a sort key. Under the documented consistency model, continuing a page with the tie-breaker yields the expected next item. A cursor reused under incompatible filters has a defined outcome. |
| Retry a creation or command after losing a response | Prefer a stable client-chosen resource URI with PUT when replacement fits. For server-assigned creation or side effects, define the idempotency key or request ID, its scope, retention, payload identity, simultaneous duplicates and replayed outcome. Scope by caller/tenant and operation. Persist deduplication atomically with the effect or equivalent durable coordination. | Same key and equivalent input within retention give one effect and a recoverable result. Reusing the key with different input yields a documented conflict. State what callers can infer after expiry. |
| Edit shared state or revalidate a cached representation | For lost updates, expose a strong ETag and require If-Match if appropriate. Return 412 when the precondition fails and describe recovery. For cache revalidation, document If-None-Match and a bodyless 304 on applicable reads. Choose Cache-Control and Vary for the representation and caller. | Two writers read the same revision. After one commits, the other's stale write receives 412. The client can re-read and reconcile. |
| Start work that may outlive an HTTP request | Define durable acceptance, 202 and a Location for an authorized status resource. Specify pending/success/failure representation, polling hints such as Retry-After, result retrieval, retention and behavior on resubmission. Include cancellation only if required. | A client can tell “accepted” from “finished.” Failure after acceptance is visible at the status resource. Access checks also protect status and result retrieval. |
| Receive changes without polling | When push is required, specify webhook event types, version, event ID, signature verification, timestamp and replay policy, acknowledgment, redelivery window and ordering guarantees. Define how the consumer deduplicates and recovers from missed deliveries. Use placeholders for keys. | Two deliveries of the same event cause one consumer-side effect. A late or out-of-order event follows the documented policy. |
| Submit a group of independent or related changes | Choose atomic batch or per-item outcomes according to the business invariant. Define maximum batch size, per-item identifiers, ordering, error representation and how to retry items safely. A single-item operation is sufficient when batching has no consumer need. | For one invalid item, verify the documented effects on the valid items and the retry scope. |

For instance, if staff retry a ticket-booking request after a mobile timeout, a request identifier protects against duplicate bookings. If two different people may take the last seat, also define the atomic capacity rule and the losing caller's outcome. These cover distinct failure cases.

Use [Google AIP-158 on pagination](https://google.aip.dev/158), [AIP-155 on request identification](https://google.aip.dev/155), [HTTP conditional requests](https://www.rfc-editor.org/rfc/rfc9110.html#section-13), [Azure's asynchronous request-reply pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/asynchronous-request-reply) and [Stripe's webhook delivery guidance](https://docs.stripe.com/webhooks) for the corresponding patterns. Provider names and delivery timings in examples are specific to those providers.
