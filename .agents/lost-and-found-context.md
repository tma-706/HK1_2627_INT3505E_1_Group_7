## Target architecture and stack

- One monorepo. Core is a Node.js 22 LTS, TypeScript, Fastify modular monolith using pg and ordered PostgreSQL SQL migrations in db/migrations/. The target entry points are apps/core/src/api.ts and apps/core/src/worker.ts. Route and job handlers call application services. Module owners enforce domain rules, authorization, and state transitions. Core and Worker are separate processes from the same codebase.
- Mobile uses Expo, React Native, and TypeScript. JavaScript packages use npm workspaces. Mobile derives request and response types from OpenAPI and calls Core through Nginx, which preserves /api/v1. For screen design use the [shared UI guidelines](../docs/design/ui-guidelines.md) and record the version applied.
- Matching uses Python and FastAPI in apps/matching/. Worker calls Matching over an internal interface with permitted processed data. Matching returns results bound to IDs and revisions. Core rechecks authorization, state, and revision before applying results. The matching index is rebuildable derived data.
- Docker Compose is the target local and CI setup. PostgreSQL stores business data and jobs. Core writes state changes and outbox events in one transaction. Worker claims jobs using FOR UPDATE SKIP LOCKED and leases, uses stable event IDs, retries with backoff, and moves exhausted jobs to DEAD. Replay retains the event ID. Media uses private S3-compatible object storage with scoped, expiring grants.
- Open decisions for implementation include sign-in choices, public location data and filters, and a realtime chat contract. The current API describes email and password, location starts from areaId, and chat uses REST. Treat experiment/v2 as research evidence and reconcile any proposed reuse against the product contract and architecture. Evaluate PostGIS only when spatial query needs are established.
